Catalyst Components · Inventory Management System

Catalyst Components Architecture

A Vue 3 single-page app on port 3000 calls a FastAPI service on port 8001 over plain HTTP. The API filters JSON data that is loaded into memory once at startup. There is no database and no authentication; the one write path is restocking orders, which stay in memory until the server restarts.

System architecture

Three layers, one direction of travel. A filter change in the browser becomes a GET request, the server filters in-memory Python lists, and the JSON response is rendered through Vue refs and computed properties.

Data flow: one filter change

What happens when someone picks Tokyo in the Location filter while the Dashboard is open.

  1. Browser · FilterBar.vue

    The <select v-model> writes selectedLocation, a ref declared at module level in useFilters.js. Because it is module-level, every component shares the same filter state and it survives route changes.

  2. Browser · Dashboard.vue

    The view's watch on all four filter refs fires and calls loadData() (Dashboard.vue:676). Only the mounted view reacts; each view registers its own watcher.

  3. Browser · useFilters.js

    getCurrentFilters() returns { warehouse: 'Tokyo', category: 'all', status: 'all' }. The month key is only added when a period other than "All Months" is selected.

  4. Browser · api.js

    Four requests go out in parallel through Promise.all: /api/dashboard/summary?warehouse=Tokyo, /api/orders?warehouse=Tokyo, /api/inventory?warehouse=Tokyo and an unfiltered /api/backlog. Any parameter equal to 'all' is left off the query string.

  5. Server · main.py

    FastAPI reads the query parameters. apply_filters() keeps rows whose warehouse is exactly "Tokyo" (category and status compare case-insensitively), and filter_by_month() does nothing because no month was sent. The rows come from lists already in memory, not from disk.

  6. Server · response

    The API returns 9 inventory items, 88 orders, a summary object and all 4 backlog items. Routes that declare a response_model are serialized through Pydantic; the summary is a plain dict.

  7. Browser · render

    Results land in refs such as allOrders and inventoryItems. Computed properties derive the status donut, order-health metrics, inventory value by category and the top-products table, and Vue re-renders only what changed.

Known gaps

Unfinished or inconsistent pieces found while mapping the code. Worth knowing before changing anything nearby.

Broken

Tasks have no backend. App.vue calls /api/tasks on every load and for add, toggle and delete; all return 404, so only the four mock tasks appear.

Broken

The purchase-order flow is a stub. Dashboard.vue:289 renders <PurchaseOrderModal>, which does not exist, and the Dashboard checks purchase_order_id while the API sends has_purchase_order, so "Create PO" always shows.

Data

Backlog and demand SKUs mostly do not exist in inventory, so any location or category filter empties the Dashboard shortages table. generate_data.py predates the current schema and would overwrite orders.json with incompatible data.

Finance

Monthly cost bars divide by a hardcoded 25000 while monthly totals run from about 145K to 555K, so bar heights overflow. The page ignores the location, category and status filters.

Dashboard

Four of the five KPIs (turnover, orders fulfilled, fill rate, processing time) are hardcoded. Only revenue comes from the API.

Structure

Reports.vue bypasses api.js and i18n; Backlog.vue is not routed; the quarter logic exists twice in main.py; everything is tied to the year 2025.

Tests

40 backend tests cover inventory, dashboard, demand, backlog and spending. Orders and reports endpoints and quarter filtering are untested, and the test docs overstate the count (51 or 55).

Config

The API base URL is hardcoded in two places, there is no Vite proxy or env config, and CORS allows every origin with credentials. Fine for a local demo, not for deployment.
